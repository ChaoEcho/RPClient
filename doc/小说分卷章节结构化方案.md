# 小说分卷章节结构化方案

## 结论

把整部小说保存在 `Story.content` 中，在篇幅增长后会同时放大编辑器状态复制、自动保存、
Room 行更新、冲突重试、Prompt 预算和导入导出的成本。更合理且不过度设计的边界是：

```text
Story（全书设置与聚合版本）
├── 未分卷 Chapter
├── Volume（可选分组）
│   └── Chapter（必选正文单元）
└── 全书 Memory / Summary / Author Note / 引用配置
```

正文以 Chapter 为唯一持久化、加载、编辑、自动保存和 AI 应用单元；Volume 只负责分组与
排序，Story 不再保存整本正文副本。一个 Story 至少保留一个 Chapter。

## 为什么这是当前最小充分方案

调研过的候选方案包括：

1. **继续使用单正文并解析 Markdown 标题**：实现最少，但标题重命名、移动和删除都变成
   大字符串重写；结构不可靠，也无法只加载一章，因此不能解决根因。
2. **Story + Chapter**：已经解决正文规模问题，但长篇内容缺少可折叠的一级组织。
3. **Story + Volume + Chapter**：只增加一个可选分组表，就能覆盖短篇、普通长篇和分卷小说。
4. **再增加 Scene / Paragraph / Block / FTS / 向量索引**：现阶段没有对应的编辑、检索或
   发布需求，会显著增加排序、迁移、撤销和 Prompt 组装复杂度，暂不实现。

因此采用第 3 种。未分卷 Chapter 让短篇无需先创建 Volume；空 Volume 允许用户先搭大纲。
删除 Volume 只解除章节归属，不删除正文。

## Room 模型

### `stories`

仅保存全书级数据：标题、Memory、滚动 Summary、Author Note、用户人设开关、世界书生成
步数、`revision` 和时间。`revision` 是 Story 聚合版本，任何章节保存、结构修改、设置修改
或世界书时序提交都会递增。

### `story_volumes`

保存 `storyId`、标题和 `sortOrder`。Story 删除时 `CASCADE`；删除 Volume 之前 Repository
会把卷内章节按原顺序追加到未分卷区域。

### `story_chapters`

保存 `storyId`、可空 `volumeId`、标题、正文、排序、`contentRevision` 和时间。

- Story 删除时 Chapter `CASCADE`。
- Volume 删除时 `volumeId SET NULL`，作为数据库级防误删兜底。
- 外键子列建立索引，符合 Room 对外键查询与删除检查的要求。
- `contentRevision` 只处理本章正文的乐观锁。

Room 官方说明 `SET_NULL` 会在父项删除时清空子项外键，且外键子列缺少合适索引会产生
警告：[Room ForeignKey](https://developer.android.com/reference/androidx/room/ForeignKey)。

数据库版本按项目约束仍为 `3`，schema 3 直接被新结构覆盖，不提供旧 `stories` 表的数据
迁移。需要注意：Room 的 destructive fallback 只在设备数据库版本与目标版本不一致且缺少
迁移路径时触发；同为 version 3 的旧 schema 不会自动重建。因此开发设备若已有旧 v3 数据，
必须清除应用数据或重新安装。官方行为说明见
[RoomDatabase.Builder](https://developer.android.com/reference/androidx/room/RoomDatabase.Builder)。

## 编辑器与内存边界

编辑器页面只读取以下内容：

- 一个完整 `StoryChapter`；
- 所有 Chapter 的轻量投影（ID、标题、分组、排序、字符数、revision）；
- Volume 列表；
- Story 级设置和引用摘要。

正文不进入可重放的 `UiState`，继续由独立 `StoryEditorDocument` 桥接。Compose 的
`TextFieldState` 以 `chapterId` 为 key，切章会创建新的输入状态，并保留同章内选区与 IME
composition。Android 官方也推荐 state-based text field，因为它统一管理文本、选区和组合态：
[Configure text fields](https://developer.android.com/develop/ui/compose/text/user-input)。

切章流程固定为：接收最后 UI 快照 → 取消防抖 → 保存当前章 → 读取目标章 → 清除本章撤销/
重做和迟到生成快照 → 发布新文档。所有 UI 快照都携带 `chapterId`，旧章节的迟到快照直接
丢弃。

## 并发与 AI 提交

采用两级 revision，而不是只检查当前正文：

```text
生成快照 = storyId + chapterId
         + baseStoryRevision + baseChapterRevision
         + 目标区间原文 hash + 世界书条目集合
```

应用结果时在一个 Room 事务内校验并更新：

1. Story 聚合 revision 未变化；
2. 目标 Chapter 的正文 revision 未变化；
3. 目标区间原文 hash 一致；
4. 世界书条目集合一致；
5. 写入章节正文、Story 世界书步数/聚合 revision 和条目运行态。

这会拒绝切章后迟到结果、生成期间修改结构/设置、正文并发保存和引用配置变化。撤销/重做
同样限定在当前章节，并在切章时清空，避免跨章节坐标失效。

Prompt 只注入当前章节正文。跨章连续性由 Story Memory、滚动 Summary、Author Note、角色
与世界书维持；摘要根据当前章节和已有 Summary 生成完整替换摘要。当前不自动拼接前后章，
避免章节数增长后 Prompt 成本重新变成 O(整本)。

## 大纲交互

仍使用一个 Activity，页面状态只增加 Editor / Outline / Settings：

- Editor 顶部显示当前 Volume 与 Chapter，点击进入 Outline。
- Outline 支持创建、重命名、上下移动和删除 Volume/Chapter，以及移动 Chapter 到其他
  Volume 或未分卷区域。
- 创建 Chapter 后直接切换到新章编辑。
- 删除当前 Chapter 后切换到相邻章；最后一章禁止删除。
- 删除 Volume 必须确认，但卷内 Chapter 全部保留。

未引入拖拽库。菜单式上下移动和目标分组选择已覆盖核心结构操作，行为明确、可测试，也避免
首版处理复杂的拖拽手势、跨容器占位和无障碍排序。

## 导入导出

`.rpstory.json` 升级为 V2，按数组顺序保存未分卷章节、Volume 和卷内 Chapter。编码只输出
V2；读取 V1 时把旧 `story.content` 转换为一个“正文”Chapter。这里兼容的是可交换文件，
不是旧 Room 数据库。

TXT / Markdown 导入不猜测标题结构，统一成为一个“正文”Chapter，避免误拆用户正文。
Markdown 和 TXT 导出逐章读取并写入 URI，不额外拼接整本字符串；结构化 JSON 归档受现有
16 MiB 导入上限约束，直接构建传输模型即可，无需首版实现流式 JSON 编码器。

## 验证矩阵

- 编译：主代码与 Android instrumentation test 源集均可编译。
- Codec：V2 往返、V1 单章映射、缺失结构、空故事、未知版本和章节上限。
- Repository：默认章创建、删卷保留章节、最后一章保护、跨章独立 revision、结构变化拒绝
  迟到 AI 结果、世界书时序原子应用与恢复。
- UI 状态：快照带 chapterId；切章重新建立 `TextFieldState`；大纲不包含正文。
- Schema：Room 导出的 version 3 schema 与 Entity/DAO 一致，外键与索引由 KSP 校验。

## 暂不实现

Scene/Block 表、章节级摘要、全书搜索、全文索引、拖拽排序、章节模板、发布排版、多人协作和
向量检索均不属于本次解决“大正文单体膨胀”的必要条件。以后只有出现明确产品需求和可验证
性能瓶颈时再独立设计。
