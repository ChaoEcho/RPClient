# 群聊聊天记录导入导出调研与开发指南

> 文档状态：开发前调研与方案设计
> 调研日期：2026-07-30
> SillyTavern 基线：1.18.0 `release` 分支，提交
> [`8172dcd`](https://github.com/SillyTavern/SillyTavern/commit/8172dcd0ee672d3cd9a5e5f7af134f91a45cd2b8)

---

## 1. 文档目的

本文档用于指导 RPClient 实现群聊聊天记录导入、导出以及 SillyTavern
兼容能力，覆盖：

1. RPClient 当前单聊归档和群聊数据模型的差异。
2. SillyTavern 群聊 JSONL 的实际文件结构和导入行为。
3. RPClient 群聊归档协议、领域模型和模块边界。
4. 群成员匹配、摘要边界、生成批次和外部文件识别策略。
5. UI、MVI、Activity Result、Room 事务和并发约束。
6. 分阶段开发任务、测试矩阵和验收标准。

本文档只讨论聊天记录及其会话级元数据。角色卡、头像、世界书正文和 Regex
脚本仍使用各自已有的导入导出能力，不随群聊 JSONL 自动打包。

---

## 2. 结论摘要

群聊聊天记录可以与 SillyTavern 实现较高程度的兼容，推荐使用：

```text
SillyTavern JSONL 标准字段
        +
chat_metadata.rpclient 扩展元数据
```

两层数据承担不同职责：

1. **SillyTavern 标准字段**保存消息正文、发言者名称、消息角色、时间、旁白类型和
   同轮群回复标识，保证文本聊天记录可以在两个应用之间交换。
2. **RPClient 扩展字段**保存群成员便携标识、角色卡指纹、成员顺序、静音状态、
   群聊生成设置、摘要边界和 RPClient 原始生成批次 ID，保证
   RPClient → RPClient 往返时尽量无损。

需要明确以下边界：

- SillyTavern 的群聊 JSONL 只是一份聊天历史，不包含完整群定义。
- SillyTavern 导入群聊时会把 JSONL 挂到用户当前选中的群，不会创建群，也不会
  导入角色卡。
- 因此可以实现“聊天记录兼容”，但不能依赖单个 JSONL 在 SillyTavern 中自动重建
  群、角色卡、头像和世界书。
- 如果未来需要完整备份，应另外设计 RPClient 自有归档包；该归档包不属于本期范围。

## 3. RPClient 当前实现基线

### 3.1 单聊归档链路

当前项目已经具备完整的单聊导入导出链路：

- [`ChatArchiveModels.kt`](../app/src/main/java/me/kafuuneko/rpclient/libs/chat/ChatArchiveModels.kt)
  定义归档领域模型。
- [`ChatArchiveCodec.kt`](../app/src/main/java/me/kafuuneko/rpclient/libs/chat/ChatArchiveCodec.kt)
  负责 SillyTavern JSONL 编解码。
- [`ChatArchiveRepository.kt`](../app/src/main/java/me/kafuuneko/rpclient/libs/chat/ChatArchiveRepository.kt)
  负责 Android `Uri` 读写、分页导出和事务导入。
- [`ChatViewModel.kt`](../app/src/main/java/me/kafuuneko/rpclient/feature/chat/ChatViewModel.kt)
  协调导出状态、生成状态和摘要状态。
- [`ChatActivity.kt`](../app/src/main/java/me/kafuuneko/rpclient/feature/chat/ChatActivity.kt)
  通过 `ActivityResultContracts.CreateDocument` 打开系统文件创建器。
- [`MainViewModel.kt`](../app/src/main/java/me/kafuuneko/rpclient/feature/main/MainViewModel.kt)
  负责读取单聊归档、要求用户确认角色映射并提交导入。

现有实现中值得复用的约束包括：

1. 最大导入文件为 32 MiB。
2. 最大消息数为 100,000。
3. 支持 BOM、空行、数字时间戳、ISO 时间戳和旧版时间格式。
4. 导出在同一 Room 事务中分页读取，按 `createTime, id` 稳定排序。
5. 导入解析和用户确认阶段不写数据库，确认后才在事务中创建会话和消息。
6. Room 本地 ID 不进入归档，摘要覆盖边界使用消息索引表达。

### 3.2 单聊模型不能直接用于群聊

现有 `ChatArchive` 只有：

```kotlin
val characterNameHint: String
val characterFingerprint: String?
```

`ChatArchiveMessage` 只保存：

```kotlin
val createTime: Long
val role: ChatArchiveMessageRole
val content: String
```

逐消息发言者不会进入最终领域消息。外部 JSONL 中的 `name` 目前只用于推断出现次数
最多的单聊角色名。因此，如果直接把 SillyTavern 群聊 JSONL 交给现有导入器，多位
角色的消息可能被压成同一个单聊角色。

正式实现群聊导入前，必须先增加文件类型识别或歧义确认，禁止这种静默降级。

### 3.3 群聊持久化数据已经具备基础条件

当前群聊数据分散在：

- [`GroupChatSession.kt`](../app/src/main/java/me/kafuuneko/rpclient/libs/room/entity/GroupChatSession.kt)
- [`GroupChatMember.kt`](../app/src/main/java/me/kafuuneko/rpclient/libs/room/entity/GroupChatMember.kt)
- [`GroupChatMessage.kt`](../app/src/main/java/me/kafuuneko/rpclient/libs/room/entity/GroupChatMessage.kt)
- [`GroupChatSummary.kt`](../app/src/main/java/me/kafuuneko/rpclient/libs/room/entity/GroupChatSummary.kt)

其中 `GroupChatMessage` 已经保存：

```kotlin
val source: Source
val content: String
val speakerCharacterId: Long?
val speakerNameSnapshot: String
val generationBatchId: String?
```

这些字段足以实现文本级群聊归档：

- `speakerNameSnapshot` 可以映射为 SillyTavern `name`。
- `generationBatchId` 可以映射为 SillyTavern `extra.gen_id`。
- `speakerCharacterId` 只用于导出时查找成员便携标识，不直接写入文件。
- 角色已删除或无法映射时，仍可保留名称快照和消息正文。

MVP 不要求修改 Room Entity。只有在未来需要无损保留 SillyTavern
Swipe、附件、推理、工具调用或任意未知 `extra` 字段时，才需要新增扩展字段并执行
数据库迁移。

## 4. SillyTavern 群聊格式调研

### 4.1 数据来源

本节结论以 SillyTavern 1.18.0 官方源码为准：

- [群聊保存和加载](https://github.com/SillyTavern/SillyTavern/blob/8172dcd0ee672d3cd9a5e5f7af134f91a45cd2b8/public/scripts/group-chats.js)
- [聊天导入导出服务端](https://github.com/SillyTavern/SillyTavern/blob/8172dcd0ee672d3cd9a5e5f7af134f91a45cd2b8/src/endpoints/chats.js)
- [聊天和群类型定义](https://github.com/SillyTavern/SillyTavern/blob/8172dcd0ee672d3cd9a5e5f7af134f91a45cd2b8/public/global.d.ts)
- [群聊官方说明](https://docs.sillytavern.app/usage/core-concepts/groupchats/)
- [Memory 扩展](https://github.com/SillyTavern/SillyTavern/blob/8172dcd0ee672d3cd9a5e5f7af134f91a45cd2b8/public/scripts/extensions/memory/index.js)

### 4.2 JSONL 文件结构

SillyTavern 群聊使用一行一个 JSON 对象的 JSONL 文件。

第一行是文件头：

```json
{
  "chat_metadata": {},
  "user_name": "unused",
  "character_name": "unused"
}
```

之后每行是一条消息：

```json
{
  "name": "Alice",
  "is_user": false,
  "is_system": false,
  "send_date": "2026-07-30T12:00:00Z",
  "mes": "Hello",
  "extra": {}
}
```

SillyTavern 保存群聊时构造文件头，然后把聊天消息依次追加到数组并写成 JSONL：

- [`group-chats.js` 保存逻辑](https://github.com/SillyTavern/SillyTavern/blob/8172dcd0ee672d3cd9a5e5f7af134f91a45cd2b8/public/scripts/group-chats.js#L623-L642)

单聊和群聊使用同一个导出接口。接口根据 `is_group` 选择单聊目录或群聊目录；导出
JSONL 时直接返回原始文件内容：

- [`script.js` 导出调用](https://github.com/SillyTavern/SillyTavern/blob/8172dcd0ee672d3cd9a5e5f7af134f91a45cd2b8/public/script.js#L11440-L11474)
- [`chats.js` 导出接口](https://github.com/SillyTavern/SillyTavern/blob/8172dcd0ee672d3cd9a5e5f7af134f91a45cd2b8/src/endpoints/chats.js#L604-L643)

### 4.3 消息字段语义

| 字段 | 语义 | RPClient 映射 |
|---|---|---|
| `name` | 当前消息显示的发言者名称 | `speakerNameSnapshot` 或会话用户名 |
| `mes` | 消息正文 | `content` |
| `is_user` | 是否为用户消息 | `Source.User` |
| `is_system` | 是否为 SillyTavern 内部/隐藏系统消息 | 默认不导入 |
| `send_date` | 消息发送时间 | `createTime` |
| `extra.type` | 特殊消息类型 | `narrator` 映射为 RPClient System |
| `extra.gen_id` | 同一次群生成轮次的消息标识 | `generationBatchId` |
| `original_avatar` | SillyTavern 角色头像文件标识 | 只作为外部匹配提示 |
| `force_avatar` | 消息显示头像 URL | MVP 不保存 |
| `extra.memory` | Memory 扩展保存的摘要 | 可映射为最新摘要 |

SillyTavern 在群聊生成角色消息时会写入角色名、头像标识和同轮
`extra.gen_id`：

- [`script.js` 群聊消息构造](https://github.com/SillyTavern/SillyTavern/blob/8172dcd0ee672d3cd9a5e5f7af134f91a45cd2b8/public/script.js#L6683-L6717)

RPClient 导出时不应把本地头像路径直接写入 `original_avatar` 或
`force_avatar`。这些值在另一套 SillyTavern 或另一台设备中通常不存在。MVP
优先依赖 `name` 匹配角色；同名角色属于必须由用户确认的歧义场景。

### 4.4 群聊导入行为

SillyTavern 的群聊导入只接受自己的 JSONL 格式。导入操作会：

1. 接收用户上传的文件。
2. 生成新的聊天文件名。
3. 把上传文件复制到群聊记录目录。
4. 把该聊天 ID 加入用户当前选中的群。

导入逻辑不会解析并创建群，也不会根据 JSONL 自动导入角色卡：

- [`group-chats.js` 导入调用](https://github.com/SillyTavern/SillyTavern/blob/8172dcd0ee672d3cd9a5e5f7af134f91a45cd2b8/public/scripts/group-chats.js#L2311-L2346)
- [`chats.js` 群聊导入接口](https://github.com/SillyTavern/SillyTavern/blob/8172dcd0ee672d3cd9a5e5f7af134f91a45cd2b8/src/endpoints/chats.js#L676-L689)

这意味着 RPClient 导出的文件在 SillyTavern 中使用时，用户应：

1. 先导入所需角色卡。
2. 创建或选择包含这些角色的群。
3. 在该群的聊天记录管理界面导入 RPClient JSONL。

### 4.5 群定义不在聊天 JSONL 中

SillyTavern 群定义是独立对象，包含：

```text
id
name
members
disabled_members
chat_id
chats
generation_mode
activation_strategy
allow_self_responses
...
```

群成员、静音和生成策略不会作为标准聊天文件头字段自动生效。因此 RPClient
可以把这些信息放在 `chat_metadata.rpclient` 中供自己恢复，但不能假设
SillyTavern 会应用这些扩展设置。

### 4.6 未知 `chat_metadata` 的保留

SillyTavern 加载群聊时读取整个 `chat_metadata`，保存时再展开写回该对象。这为
`chat_metadata.rpclient` 提供了兼容空间。RPClient 扩展字段不应覆盖
SillyTavern 已有字段，也不应写入 SillyTavern `integrity` 值。

`integrity` 是 SillyTavern 当前安装用于防止并发覆盖的本地标识。跨应用导出时省略
即可，由 SillyTavern 加载后自行生成。

## 5. 兼容目标

### 5.1 兼容等级

本功能定义三个兼容等级：

#### A. 文本历史兼容

必须实现：

- 用户、角色和旁白消息。
- 每条消息的发言者名称。
- 正文和消息时间。
- 同轮群回复分组。
- SillyTavern JSONL 导入和导出。

#### B. RPClient 会话无损往返

必须实现：

- 群标题和用户名。
- 成员顺序、静音状态和角色指纹。
- 场景、用户描述、用户笔记。
- Prompt 覆盖和群生成设置。
- 最新摘要及其覆盖消息边界。
- RPClient 原始 `generationBatchId`。

#### C. SillyTavern 富消息无损往返

暂不实现：

- Swipe 及 `swipe_info`。
- 图片、音频、视频和文件附件。
- 推理内容。
- Tool call。
- 任意第三方扩展写入的消息 `extra`。
- SillyTavern 头像文件引用。

若未来要求 C 级兼容，需要为群聊消息新增可恢复扩展 JSON，并定义安全过滤和 Room
迁移策略。

### 5.2 字段兼容矩阵

| RPClient 数据 | SillyTavern 标准字段 | 目标 |
|---|---|---|
| 消息正文 | `mes` | 双向完整 |
| 发言者名称 | `name` | 双向完整 |
| 用户/角色 | `is_user` | 双向完整 |
| RPClient System | `extra.type = "narrator"` | 双向完整 |
| 时间 | `send_date` | 双向完整 |
| 生成批次 | `extra.gen_id` | 保留批次关系 |
| 场景覆盖 | `chat_metadata.scenario` | 双向完整 |
| 系统 Prompt 覆盖 | `chat_metadata.system_prompt` | 双向完整 |
| 用户笔记 | `note_prompt` 等字段 | 双向基本完整 |
| 最新摘要 | `extra.memory` | 与 Memory 扩展互通 |
| 摘要精确边界和创建时间 | `chat_metadata.rpclient.summary` | RPClient 无损 |
| 成员、排序、静音 | 无聊天文件标准字段 | RPClient 扩展 |
| 群发言策略 | 无聊天文件标准字段 | RPClient 扩展 |
| 自动模式和裁剪设置 | 无聊天文件标准字段 | RPClient 扩展 |
| 用户描述 | 无稳定标准字段 | RPClient 扩展 |
| 世界书本地 ID/运行状态 | 无可迁移语义 | 默认不跨设备恢复 |

## 6. 建议的归档协议

### 6.1 文件类型

- 扩展名：`.jsonl`
- MIME：`application/x-ndjson`
- 字符集：UTF-8
- 一行一个 JSON 对象
- 允许 UTF-8 BOM 和空行

### 6.2 文件头

建议文件头：

```json
{
  "chat_metadata": {
    "scenario": "共同场景",
    "system_prompt": "群聊系统提示词",
    "note_prompt": "用户笔记",
    "note_depth": 4,
    "note_position": 1,
    "note_role": 0,
    "rpclient": {
      "archive_type": "group",
      "schema_version": 1,
      "title": "冒险小队",
      "create_time": 1785398400000,
      "latest_time": 1785398500000,
      "user_name": "You",
      "user_description": "",
      "auto_summary_paused": false,
      "members": [
        {
          "key": "m0",
          "name": "Alice",
          "fingerprint": "sha256...",
          "sort_order": 0,
          "muted": false
        },
        {
          "key": "m1",
          "name": "Bob",
          "fingerprint": "sha256...",
          "sort_order": 1,
          "muted": false
        }
      ],
      "settings": {
        "activation_strategy": "Natural",
        "allow_self_responses": false,
        "character_card_mode": "Swap",
        "include_muted_cards": false,
        "auto_mode_enabled": false,
        "trim_other_speakers": true,
        "system_prompt_override": "群聊系统提示词",
        "group_nudge_prompt_override": "",
        "new_group_chat_prompt_override": ""
      },
      "summary": {
        "content": "最近摘要",
        "create_time": 1785398490000,
        "covered_message_index": 42
      }
    }
  },
  "user_name": "unused",
  "character_name": "unused"
}
```

协议约束：

1. `archive_type` 必须是 `"group"`。
2. `schema_version` 初始为 `1`。
3. `members[].key` 是文件内部稳定键，例如 `m0`、`m1`，不能使用 Room ID。
4. `fingerprint` 复用 `ChatCharacterMatcher.fingerprintOf()` 的角色卡内容指纹。
5. `covered_message_index` 是归档普通消息数组的零基索引；`-1` 表示摘要未覆盖消息。
6. 未知新字段必须被旧版 RPClient 忽略。
7. 导入器遇到高于自身支持范围的主版本时必须拒绝，不得猜测写库。

### 6.3 消息行

用户消息：

```json
{
  "name": "You",
  "is_user": true,
  "is_system": false,
  "send_date": "2026-07-30T12:00:00Z",
  "mes": "大家好",
  "extra": {}
}
```

角色消息：

```json
{
  "name": "Alice",
  "is_user": false,
  "is_system": false,
  "send_date": "2026-07-30T12:00:01Z",
  "mes": "你好！",
  "extra": {
    "gen_id": 1,
    "rpclient": {
      "member_key": "m0",
      "generation_batch_id": "0e330245-8ed7-4da8-9aef-4ad022924d37"
    }
  }
}
```

旁白消息：

```json
{
  "name": "Narrator",
  "is_user": false,
  "is_system": false,
  "send_date": "2026-07-30T12:00:02Z",
  "mes": "门缓缓打开。",
  "extra": {
    "type": "narrator"
  }
}
```

### 6.4 `gen_id` 生成规则

SillyTavern 使用 `extra.gen_id` 判断连续角色消息是否属于同一轮群回复。RPClient 的
`generationBatchId` 是字符串，SillyTavern 类型定义期望数字。

建议导出时：

1. 按消息顺序维护 `generationBatchId → 正整数` 映射。
2. 每个首次出现的非空批次依次分配 `1, 2, 3...`。
3. 同一批次的所有消息写入相同 `extra.gen_id`。
4. 同时在 `extra.rpclient.generation_batch_id` 中保存原始字符串。
5. 没有批次的消息不写 `gen_id`。

该方案不依赖哈希，没有 JavaScript 安全整数和碰撞问题。

导入 SillyTavern 文件时：

- 优先读取 `extra.rpclient.generation_batch_id`。
- 否则把同值的 `extra.gen_id` 规范化为同一个本地字符串批次。
- 缺失 `gen_id` 时保持 `generationBatchId = null`。

### 6.5 摘要兼容

RPClient 的摘要有明确覆盖消息边界；SillyTavern Memory 扩展则把摘要放在某条消息的
`extra.memory` 中。

导出时应同时写入：

1. `chat_metadata.rpclient.summary`：保存正文、创建时间和精确索引。
2. 被摘要覆盖的最后一条消息的 `extra.memory`：供 SillyTavern Memory 扩展读取。

导入时优先级：

1. 优先读取受支持版本的 `rpclient.summary`。
2. 没有 RPClient 元数据时，从后向前查找最后一个非空 `extra.memory`。
3. 找到 `extra.memory` 的消息索引就是覆盖边界。
4. 索引超界时忽略摘要并记录脱敏诊断，不允许关联到错误消息。

### 6.6 用户笔记兼容

RPClient 用户笔记固定以 System role、深度 4 注入历史。可映射为 SillyTavern
Author's Note 默认语义：

```json
{
  "note_prompt": "用户笔记",
  "note_interval": 1,
  "note_depth": 4,
  "note_position": 1,
  "note_role": 0
}
```

导入外部文件时只读取 `note_prompt` 作为 RPClient 用户笔记。SillyTavern 其他位置、
深度和角色组合无法由 RPClient 当前模型完整表达，应在导入预览中提示“已按 RPClient
固定位置导入”，不能假装无损。

### 6.7 世界书字段

`lorebookEntrySet` 保存的是本地条目 ID，`worldInfoStateJson` 还包含
sticky/cooldown 等本地运行状态。它们不具备跨设备稳定语义。

建议：

1. SillyTavern 互通文件不写标准世界书绑定字段。
2. RPClient 扩展可以保留原始信息用于诊断，但默认导入时清空。
3. 若未来支持同设备恢复，必须逐个校验条目 ID 是否存在，并让用户明确选择恢复。
4. 不得把来源设备 ID 静默绑定到目标设备同号但不同内容的条目。

## 7. 建议的领域模型

不要继续扩展单聊 `ChatArchive` 表达群聊。建议新增独立模型：

```kotlin
data class GroupChatArchive(
    val title: String,
    val createTime: Long,
    val latestTime: Long,
    val userName: String,
    val userDescription: String,
    val scenario: String,
    val userNote: String,
    val autoSummaryPaused: Boolean,
    val settings: GroupChatArchiveSettings,
    val members: List<GroupChatArchiveMember>,
    val messages: List<GroupChatArchiveMessage>,
    val summary: GroupChatArchiveSummary?
)

data class GroupChatArchiveMember(
    val key: String,
    val nameHint: String,
    val characterFingerprint: String?,
    val sortOrder: Int,
    val muted: Boolean,
    val externalAvatarHint: String? = null
)

data class GroupChatArchiveMessage(
    val createTime: Long,
    val role: GroupChatArchiveMessageRole,
    val content: String,
    val speakerName: String,
    val speakerMemberKey: String?,
    val generationBatchId: String?

enum class GroupChatArchiveMessageRole {
    User,

}

data class GroupChatArchiveSummary(
    val content: String,
    val createTime: Long,

```

`externalAvatarHint` 只参与导入预选，不能成为本地持久化关联键。

统一文件入口可以返回：

```kotlin
sealed interface ChatArchiveDraft {
    data class Single(val archive: ChatArchive) : ChatArchiveDraft
    data class Group(val archive: GroupChatArchive) : ChatArchiveDraft
    data class Ambiguous(val parsed: ParsedChatArchive) : ChatArchiveDraft
```

如果不希望一次重构现有单聊入口，也可以先让新群聊读取器与单聊读取器并列，但必须
共享文件类型探测器，避免两个 Codec 对同一群聊文件给出相互冲突的成功结果。

## 8. Codec 与 Repository 架构

### 8.1 推荐拆分

```text
libs/chat/
├── SillyTavernJsonlCodec.kt          # 通用文件头、消息行、时间和安全限制
├── ChatArchiveCodec.kt               # 单聊领域适配
├── ChatArchiveRepository.kt
├── GroupChatArchiveModels.kt
├── GroupChatArchiveCodec.kt          # 群聊领域适配
├── GroupChatArchiveDetector.kt
└── GroupChatArchiveRepository.kt
```

如果抽取 `SillyTavernJsonlCodec` 会导致首期改动过大，可以让
`GroupChatArchiveCodec` 独立实现，但时间解析、大小限制和消息上限必须与现有单聊
保持一致，并通过共享测试 fixture 防止行为漂移。

### 8.2 Codec 职责

Codec 负责：

- JSONL 逐行解析和写入。
- 文件头与消息行字段映射。
- 版本检查。
- 时间解析和规范化。
- 系统消息过滤和旁白识别。
- `gen_id` 与摘要字段转换。
- 未知字段忽略。
- 纯内存领域模型转换。

Codec 不负责：

- Android `Uri`。
- Room 查询和写入。
- 角色选择。
- UI 文案和 Toast。
- 群成员业务校验。

### 8.3 Repository 职责

`GroupChatArchiveRepository` 负责：

- 通过 Application Context 读写 `Uri`。
- 在 Room 事务中加载导出元数据。
- 分页读取消息并流式写出。
- 根据用户确认的映射原子导入会话、成员、消息和摘要。
- 验证角色仍存在且选择不重复。
- 处理摘要消息索引到新 Room ID 的转换。
- 对失败进行回滚。

Repository 不持有 UI 状态，不生成 Toast，不依赖 Activity 或 Compose。

新增 Codec 和 Repository 后，应在
[`RPClientApp.kt`](../app/src/main/java/me/kafuuneko/rpclient/RPClientApp.kt)
注册 Koin 单例。

### 8.4 分页导出

现有 [`GroupChatMessageDao.kt`](../app/src/main/java/me/kafuuneko/rpclient/libs/room/dao/GroupChatMessageDao.kt)
只有完整历史查询。群聊导出不应调用 `getGroupChatData()` 一次加载全部消息。

应新增与单聊一致的稳定分页查询：

```sql
SELECT * FROM group_chat_messages
WHERE sessionId = :sessionId
  AND (
    createTime > :afterCreateTime
    OR (createTime = :afterCreateTime AND id > :afterMessageId)
  )
ORDER BY createTime ASC, id ASC
LIMIT :limit
```

整个导出在同一 Room 读取事务中完成，避免分页之间混入新消息或编辑结果。

### 8.5 原子导入

确认导入后，在一个 `withTransaction` 中：

1. 再次验证所有选中角色存在。
2. 验证成员 ID 去重后至少有两个。
3. 创建 `GroupChatSession`。
4. 按归档顺序写入 `GroupChatMember`。
5. 批量写入 `GroupChatMessage`，保存新消息 ID 列表。
6. 将摘要 `coveredMessageIndex` 转换为新消息 ID。
7. 写入 `GroupChatSummary`。
8. 更新 `latestTime`。

任何一步失败都不得留下半成品会话。

不要复用当前 `GroupChatRepository.createSession()` 执行导入，因为该方法会按新建群聊
语义处理开场消息和默认设置。导入需要保留原始消息、时间和摘要边界，应使用独立的
`saveImport()` 事务入口。

## 9. 文件类型识别

### 9.1 明确类型

如果文件头包含：

```json
"chat_metadata": {
  "rpclient": {
    "archive_type": "group"
  }
}
```

则直接识别为群聊。

`archive_type = "single"` 可以在后续单聊协议版本中补充；兼容现有单聊文件时不能
强制要求该字段。

### 9.2 外部 SillyTavern 文件

外部文件没有 RPClient 类型字段时，按消息统计不同 AI 发言者：

1. 忽略 `is_user = true`。
2. 忽略 `is_system = true`。
3. 忽略 `extra.type = narrator`。
4. 优先用非空 `original_avatar` 区分身份。
5. 否则用清理后的 `name` 区分身份。

建议判定：

- 至少两个不同 AI 身份：群聊。
- 只有一个 AI 身份且出现群聊特征：歧义。
- 没有群聊特征：单聊。

群聊特征包括：

- 消息包含 `original_avatar`。
- 消息包含 `extra.gen_id`。
- 文件有多个角色名。

`gen_id` 也可能由扩展写入单聊，因此不能单独作为强判据。

### 9.3 歧义处理

以下文件无法可靠自动判断：

- 群聊历史中只有一个角色发过言。
- 多个同名角色发言且缺少 `original_avatar`。
- 单聊历史通过 `/sendas` 等功能包含其他发言者。

必须显示“作为单聊导入 / 作为群聊导入”的用户确认，不得静默选择。

在正式群聊导入完成前，可以先实现保护：检测到多个 AI 发言者时拒绝走单聊导入，并
提示当前版本暂不支持群聊导入。

## 10. 群成员映射

### 10.1 自动建议顺序

每个归档成员按以下顺序预选本地角色：

1. RPClient 角色卡指纹唯一匹配。
2. 角色名称忽略大小写后的唯一精确匹配。
3. SillyTavern `original_avatar` 去扩展名后与唯一角色名称匹配，仅作为弱提示。
4. 无唯一结果时不自动选择。

指纹和名称只负责建议，最终必须由用户确认。重复角色卡、同名角色或同一角色被映射到
多个归档成员时都不能自动提交。

### 10.2 导入对话框状态

解析得到的完整 `GroupChatArchive` 属于较大且敏感的导入草稿，应保存在
`MainViewModel` 私有字段，不进入 `UiState`。

UiState 只保存渲染需要的数据：

```kotlin
data class ImportGroupChatMemberMapping(
    val archiveMemberKey: String,
    val sourceName: String,
    val selectedCharacterId: Long?,
    val matchKind: MatchKind
)
```

对话框至少展示：

- 来源群标题。
- 消息数。
- 识别出的角色发言者数。
- 每个来源成员及本地角色选择。
- 无法绑定的历史发言者数量。
- SillyTavern 外部设置可能有损的提示。

### 10.3 缺失成员

群聊继续生成要求至少两个有效本地角色，但历史消息不应因为角色缺失而丢失。

建议规则：

- 归档成员用于当前群时必须映射到有效角色。
- 历史中不属于当前成员或角色已删除的角色消息可以：
  - `speakerCharacterId = null`
  - 保留 `speakerNameSnapshot`
- 用户必须最终选择至少两个不同角色作为当前群成员。
- 不允许同一个本地角色同时映射到两个归档成员。

## 11. 群设置映射

### 11.1 RPClient 扩展设置

以下设置保存在 `chat_metadata.rpclient.settings`：

| RPClient 字段 | 协议值 |
|---|---|
| `activationStrategy` | `Manual` / `Natural` / `List` / `Pooled` |
| `allowSelfResponses` | Boolean |
| `characterCardMode` | `Swap` / `Join` |
| `includeMutedCards` | Boolean |
| `autoModeEnabled` | Boolean |
| `trimOtherSpeakers` | Boolean |
| `systemPromptOverride` | String |
| `groupNudgePromptOverride` | String |
| `newGroupChatPromptOverride` | String |

协议使用语义字符串，不使用 Kotlin enum ordinal，也不使用 SillyTavern 数字枚举，避免
双方枚举顺序变化造成错配。

未知枚举值应回退到 RPClient 默认值并在导入预览中提示，不能调用 `valueOf()` 直接
崩溃。

### 11.2 SillyTavern 群设置参考

SillyTavern 群定义中的数值语义为：

```text
activation_strategy:
0 = Natural
1 = List
2 = Manual
3 = Pooled

generation_mode:
0 = Swap
1 = Join，排除非当前静音角色
2 = Join，包含静音角色
```

如果未来支持导入独立 SillyTavern 群定义，应按语义映射：

```text
generation_mode 0 -> Swap
generation_mode 1 -> Join + includeMutedCards=false
generation_mode 2 -> Join + includeMutedCards=true
```

本期聊天 JSONL 不包含独立群定义，不能从标准文件恢复这些值。

### 11.3 原生聊天元数据

可同时写入 SillyTavern 原生字段：

| RPClient | SillyTavern |
|---|---|
| `scenario` | `chat_metadata.scenario` |
| `systemPromptOverride` | `chat_metadata.system_prompt` |
| `userNote` | `note_prompt`、`note_depth`、`note_position`、`note_role` |

RPClient 导入自己导出的文件时，以 `chat_metadata.rpclient` 为权威；外部文件则读取
SillyTavern 原生字段。

## 13. 安全、隐私和错误处理

聊天导出可能包含私密对话、用户描述、角色设定、系统 Prompt 和摘要。实现时必须：

1. 只有用户明确点击导出才创建文件。
2. 默认文件名使用时间戳或经过清理的短标题，不包含消息正文。
3. Toast 和普通日志不输出完整文件内容、私密对话或真实目标路径。
4. JSON 解析异常只显示“文件格式无效”等脱敏信息。
5. 详细异常只用于受控调试，不进入普通请求日志。
6. 导入前限制文件大小和消息数，避免内存耗尽。
7. 限制单行 JSON 和字符串长度，避免少量超大字段绕过消息数限制。
8. 不加载外部 `force_avatar` URL，不在导入过程中发起网络请求。
9. 不执行外部文件中的脚本或未知扩展字段。
10. 导入失败后不留下会话、成员、消息或摘要半成品。

建议沿用现有 32 MiB 和 100,000 消息上限，并增加：

- 单行最大长度。
- 标题、名称和普通设置字段最大长度。
- `members` 最大数量。
- `chat_metadata.rpclient` 嵌套深度和数组长度检查。

9. 群成员唯一匹配正确预选。
10. 重名角色不自动选择。
11. 保存期间禁止修改映射和重复确认。
12. 成功后刷新首页并打开新群聊。

### 15.5 SillyTavern 手工互操作测试

RPClient → SillyTavern：

1. 在 RPClient 创建至少两个成员的群。
2. 生成包含用户消息、两个角色同轮回复、旁白和摘要的记录。
3. 导出 JSONL。
4. 在 SillyTavern 安装对应角色卡并创建群。
5. 从该群的聊天记录管理页导入 JSONL。
6. 验证名称、正文、时间顺序和旁白。
7. 触发重新生成，检查同轮 `gen_id` 分组行为。
8. 启用 Memory 扩展，检查摘要是否可读取。

SillyTavern → RPClient：

1. 在 SillyTavern 创建群聊和多角色回复。
2. 导出原始 JSONL。
3. 在 RPClient 导入并确认成员映射。
4. 验证消息归属、名称快照和批次。
5. 验证摘要和继续生成。
6. 再次导出并导回 SillyTavern。

## 16. 验收标准

功能完成至少满足：

1. RPClient 群聊页可以把当前记录导出为 UTF-8 JSONL。
2. 导出文件可被 SillyTavern 1.18.0 导入到已有群中并正确显示文本历史。
3. RPClient 可以导入 SillyTavern 群聊 JSONL，并要求用户确认多个角色映射。
4. 不会把明确群聊静默导入为单聊。
5. 同轮回复的 `generationBatchId` 在 RPClient 往返后保持一致。
6. 最新摘要正文和覆盖边界在 RPClient 往返后保持一致。
7. 导入失败不会留下半成品 Room 数据。
8. 大型导出使用稳定分页，不随消息总量额外复制完整历史。
9. 生成、摘要和导出不会并发写入同一会话快照。
10. 文件内容、真实路径和私密消息不会进入普通 Toast 或日志。
11. 所有新增 Codec、探测、Repository 和 ViewModel 行为都有对应测试。
12. 项目单元测试和 Debug 构建通过。

## 17. 已知风险和待决策项

### 17.1 同名角色

只依赖 `name` 无法区分同名 SillyTavern 角色。RPClient 自有文件使用成员 key 和指纹
解决；外部文件必须要求用户确认。

### 17.2 只有一个角色发言的群聊

无法从标准 JSONL 可靠判断是单聊还是群聊，必须显示类型选择。

### 17.3 Rich message 有损

当前 Room 模型无法保存 Swipe、附件、推理和工具调用。首期应明确提示，而不是悄悄
宣称完全兼容。

### 17.4 用户笔记位置差异

RPClient 只能表达固定的 System/深度 4 语义。外部文件的其他 Author's Note
配置会被规范化。

### 17.5 自动模式

SillyTavern 的自动模式启用状态更接近运行时 UI 状态，不是聊天 JSONL 的标准字段。
RPClient 只在自己的扩展元数据中保存，不期望 SillyTavern 自动应用。

### 17.6 完整群备份

如果产品后续要求“一次导入群、角色卡、头像、世界书和记录”，应设计独立的
`.zip` 或专用扩展名归档，并明确其不是 SillyTavern 原生聊天文件。不要向本期 JSONL
持续塞入二进制资源。
